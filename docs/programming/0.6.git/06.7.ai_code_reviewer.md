# Revisor automático de PRs (Code Reviewer con IA)

El Code Reviewer es un pipeline de Azure DevOps que revisa el diff de cada Pull Request con un modelo de IA (Gemini) y deja comentarios en el PR. Es una ayuda para el revisor humano, no un sustituto.

Configuración paso a paso del pipeline en un repositorio: wiki `SCISA_Packages` → *Configuración CodeReviewer*.

---

## 1. Qué es y qué NO es

**Es:**
- Una primera revisión rápida y constructiva sobre el diff del PR.
- Un recordatorio automático de estándares (CHANGELOG, versión, principios de código, riesgo de bugs).

**No es:**
- Una aprobación. No cuenta para las aprobaciones requeridas en [06.4](./06.4.pullrequest.md): el PR sigue necesitando al menos una aprobación humana (dos en cambios críticos).
- Un merge automático. El bot solo comenta; nunca completa el PR.
- Fuente de verdad. Si el bot y las guías discrepan, mandan las guías y se corrige el bot (ver §5).

> Un PR sin comentarios del bot no es un PR bien revisado. Un comentario del bot no es una orden: el autor lo evalúa con criterio técnico, igual que el de cualquier revisor ([010.4](../010.team%20communication/010.4.codes_of_conduct_pr.md)).

---

## 2. Dónde vive

| Elemento | Ubicación |
|---|---|
| Plantilla y prompt | Repositorio `SCISA_Packages/SCISA_Packages`, archivo `CodeReview.yml` (rama `main`) |
| Uso en cada repo | Pipeline YAML propio con `template: CodeReview.yml@prtemplates`, `trigger: none`, `pr: none` |
| Disparo | Build Validation en la rama protegida |
| Secretos | Azure Key Vault (`kv-devopspipelines`) |

Restricciones actuales: solo se ejecuta en las primeras 3 iteraciones del PR; si el diff no tiene cambios, no hace nada.

## 3. Qué revisa hoy

| Revisión | Tipo | Origen |
|---|---|---|
| CHANGELOG actualizado, en lenguaje de negocio | Local (presencia de archivo) + IA (contenido) | [05.5 DoD](../0.5.collaborative_work/05.5.DoD.md) |
| Cambio de versión (`AssemblyInfo`, `Directory.Build.targets`, `package.json`) | Local + IA | [07.3](../0.7.repositories/07.3.semantic_versioning.md) |
| SOLID, DRY, uso correcto de `async/await` | IA | [06.4](./06.4.pullrequest.md) |
| Magic strings/numbers, excepciones específicas, claridad | IA | [06.4](./06.4.pullrequest.md) |
| Consistencia entre capas, acceso a base de datos | IA | [06.4](./06.4.pullrequest.md) |
| Riesgo de bugs, solo en líneas modificadas | IA | — |

## 4. Qué NO revisa hoy (roadmap)

La documentación BDD y las pruebas automáticas se están adoptando en la organización; el bot debe acompañar esa adopción **sin bloquear antes de tiempo**.

### Modos por regla

Cada regla nueva se despliega en tres modos, configurables por repositorio como parámetro de la plantilla:

| Modo | Comportamiento |
|---|---|
| `off` | No se evalúa. |
| `warn` | Comenta en el PR; no bloquea. Modo inicial de toda regla nueva. |
| `enforce` | Falla el build validation; el PR no puede mergearse sin corregir o justificar. |

Una regla pasa de `warn` a `enforce` solo cuando el equipo dueño del repositorio ya tiene el hábito instalado y la tasa de falsos positivos es baja.

### Fases

**Fase 1 — Reglas locales y deterministas (sin IA), modo `warn`**

| Regla | Origen |
|---|---|
| Código fuente modificado sin archivos de prueba modificados | [07.4 §7](../0.7.repositories/07.4.minimum_automated_tests.md) |
| Código nuevo sin `docs/features/<feature>/<feature>.feature` | [05.6 §3](../0.5.collaborative_work/05.6.min_docs.md), [05.15](../0.5.collaborative_work/05.15.spec_first_workflow.md) |
| `.feature` modificado sin su `.md` (o viceversa) | [05.6 §3](../0.5.collaborative_work/05.6.min_docs.md) |
| `.feature` sin `# language: es` | [05.6 §3](../0.5.collaborative_work/05.6.min_docs.md) |
| `TODO` sin ticket asociado | [06.4](./06.4.pullrequest.md) |
| Título del PR fuera de `<tipo>(<scope>): <intención>` | [06.3](./06.3.commits_rules.md), [06.4](./06.4.pullrequest.md) |
| Cambios de variables de entorno o setup sin `README` | [05.6 §7](../0.5.collaborative_work/05.6.min_docs.md) |

**Fase 2 — Revisión con IA**

- Escenarios que solo cubren el camino feliz (sin casos borde).
- Consistencia entre el `.feature` y el comportamiento del código del diff.
- Pruebas unitarias que acceden a base de datos, red o infraestructura real ([07.4 §3.2](../0.7.repositories/07.4.minimum_automated_tests.md)).
- Corrección de bug sin prueba de regresión ([07.4 §3.3](../0.7.repositories/07.4.minimum_automated_tests.md)).
- Pruebas que validan solo el camino feliz ([07.4 §11](../0.7.repositories/07.4.minimum_automated_tests.md)).
- Cambio arquitectónico sin ADR ([05.6 §4](../0.5.collaborative_work/05.6.min_docs.md)).
- Niveles de severidad en comentarios (bloqueante / mejora / sugerencia), alineados a [010.4](../010.team%20communication/010.4.codes_of_conduct_pr.md).

**Fase 3 — `enforce` selectivo**

- Reglas de Fase 1 seleccionadas pasan a `enforce` repo por repo.
- Excepción justificada: un PR sin pruebas o sin BDD debe explicar el motivo en la descripción ([07.4 §7](../0.7.repositories/07.4.minimum_automated_tests.md)); el bot lo reconoce y no bloquea.
- No aplican (se omiten) los PRs que no cambian comportamiento: solo documentación, dependencias, formato.

## 5. Cómo proponer mejoras al revisor

El prompt y las reglas se versionan en `SCISA_Packages`. Cualquier persona puede proponer cambios.

### 5.1 Cuándo proponer

- **Falso positivo:** el bot reporta algo que no es un problema.
- **Falso negativo:** el bot no detectó algo que una guía exige.
- **Ruido o tono:** comentarios repetitivos, vagos o con tono inadecuado.
- **Regla nueva:** una guía cambió o se adoptó un estándar nuevo.
- **Falla técnica:** el pipeline se rompe, se salta o reporta resultados incorrectos.

### 5.2 Paso a paso

1. **Registrar la sugerencia** en ClickUp, con tipo `Task` (o `Bug` si es una falla técnica) y la etiqueta `code-reviewer`. Incluir:
   - Link al PR y al comentario del bot.
   - Qué se esperaba vs. qué ocurrió.
   - Sección de guía que lo respalda (ej. `07.4 §3.3`).
   - Tipo: falso positivo / falso negativo / tono / regla nueva / falla técnica.
2. **Proponer el cambio** con un PR a `SCISA_Packages` sobre `CodeReview.yml`:
   - Descripción con el motivo y el ticket de ClickUp.
   - Diff del prompt o regla, antes y después.
   - Evidencia: resultado de correrlo contra 2–3 PRs reales (con y sin el problema).
   - Entrada en el CHANGELOG del paquete.
3. **Revisar y aprobar** según [06.4](./06.4.pullrequest.md); la aprobación corresponde al responsable del paquete `SCISA_Packages`.
4. **Publicar:** al mergear a `main`, todos los repos que usan la plantilla reciben el cambio. Si el cambio introduce una regla nueva, entra en modo `warn`.

### 5.3 Reglas para modificar el prompt

- Cada regla cita la guía que la origina; si no existe guía, primero se escribe la guía.
- Reglas concretas y verificables sobre el diff; nada de "mejora el código".
- Salida estructurada; si el prompt indica una frase para el caso sin hallazgos, el esquema de salida debe contemplarla.
- Tono constructivo, sin lenguaje disciplinario.
- Los cambios se prueban antes de mergear; un prompt peor genera ruido en todos los repositorios a la vez.

## 6. Responsabilidades

| Rol | Responsabilidad |
|---|---|
| Autor del PR | Evaluar cada comentario del bot; resolverlo o responder con justificación técnica. |
| Revisor humano | No delegar en el bot. Revisar diseño, intención y riesgo igual. |
| Responsable de `SCISA_Packages` | Mantener `CodeReview.yml`, aprobar cambios al prompt, vigilar costo y falsos positivos. |
| Equipo dueño del repo | Decidir el modo (`off`/`warn`/`enforce`) de cada regla para su repositorio. |
