# Criterios para Definition of Ready (DoR)

El **Definition of Ready** es lo que se necesita **antes** de empezar a trabajar un ticket, para no perder tiempo en reuniones infinitas o suposiciones.

> **Regla dura:** si un ticket no cumple el DoR, **no se toma**. Quien lo encuentre sin criterios claros de éxito lo regresa al analista o a la pareja que lo escribió. "Ni le empiecen."

La responsabilidad de que un ticket esté Ready es del **Analista / PO junto con su par** (nadie lo trabaja solo). Quien lo toma verifica el checklist antes de empezar.

## Checklist de Ready

| Elemento | Por qué es importante |
|---|---|
| **Contexto de negocio (el por qué)** | Saber **para qué** sirve lo que se programa ayuda a tomar mejores decisiones técnicas. |
| **Spec BDD validada** | Escenarios en español (`# language: es`) validados por una persona distinta al autor, con el registro de aprobación en ClickUp. Ver [05.15](./05.15.spec_first_workflow.md). |
| **Criterios de aceptación (AC) claros** | Si no hay una lista Sí / No, no hay forma de saber si terminó. |
| **Diseños / mocks finales** | Si hay UI, aprobada (Figma o equivalente). Evita el "esto no se ve como pensaba". |
| **Dependencias identificadas** | ¿Necesita un endpoint, un dato o una decisión de otro equipo? Si no está listo, el ticket no está Ready. |
| **Datos de prueba disponibles** | Acceso a una base de datos o mocks para probar escenarios reales. |
| **Alcance explícito** | Qué **no** entra en el ticket. |
| **Impacto de versión estimado** | PATCH / MINOR / MAJOR esperado (ver [versionamiento](../0.7.repositories/07.3.semantic_versioning.md)). |

## Estados en ClickUp

| Estado | Significado |
|---|---|
| **New** | Backlog. Todo lo que se va agregando. Puede estar incompleto. |
| **Pending** | Trabajo **asignado y listo para trabajar**. Solo se llega aquí si cumple el DoR. |

El movimiento **New → Pending** es el momento en que se verifica el DoR. Un ticket con descripción como "error" no pasa.

## Cómo se llega a Ready

1. Sesión de refinamiento (analista + dev/par): se entiende el problema y se acuerdan los escenarios.
2. Se escribe la spec y los AC.
3. Un par distinto valida la spec.
4. El ticket se completa (usar la skill `ticket-template`) y pasa a **Pending**.

## Relación con el DoD

El DoR responde "¿puedo empezar?". El **Definition of Done** responde "¿terminé?". Ver [05.5 DoD](./05.5.DoD.md).
