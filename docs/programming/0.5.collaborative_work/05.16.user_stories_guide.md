# Guía de Historias de Usuario

Una historia de usuario describe una necesidad del usuario desde su perspectiva, con el detalle justo para conversarla, estimarla y verificarla. Es el artefacto base del [pre-análisis](./05.14.pre_analysis_standard.md), de los tickets de tipo Feature y de la spec del flujo [Spec-First](./05.15.spec_first_workflow.md).

Esta guía define **cómo escribir una buena historia**. El formato mínimo exigido en propuestas está en el estándar de pre-análisis; aquí se profundiza.

---

## Formato

> **Como** [rol], **quiero** [acción], **para** [beneficio].

| Parte | Qué debe contener | Error común |
|---|---|---|
| **Rol** | Persona o perfil concreto que usa el sistema (Analista PLD, Oficial de Cumplimiento, Operador de cobranza) | "Como usuario" o "Como el sistema" |
| **Acción** | Qué necesita hacer, en términos de negocio | Describir la solución técnica ("quiero un botón que llame al endpoint X") |
| **Beneficio** | Valor o problema que se resuelve | Omitirlo o repetir la acción con otras palabras |

Si el beneficio no se puede explicar, la historia probablemente no debería hacerse.

---

## Criterios de calidad (INVEST)

| Criterio | Pregunta de verificación |
|---|---|
| **I**ndependiente | ¿Se puede desarrollar y entregar sin esperar otra historia? |
| **N**egociable | ¿Describe el qué y deja abierto el cómo? |
| **V**aliosa | ¿El usuario o el negocio notan la diferencia al entregarla? |
| **E**stimable | ¿El desarrollador entiende lo suficiente para estimarla? |
| **S**ana de tamaño (*Small*) | ¿Cabe en un sprint? Si no, se divide |
| **T**esteable | ¿Se puede verificar con criterios de aceptación concretos? |

---

## Criterios de aceptación

Cada historia lleva criterios de aceptación en formato BDD (Given/When/Then), alineados con el estándar de pre-análisis.

```gherkin
Escenario: Alta de operación inusual con monto sobre umbral
  Dado que soy Analista PLD con la operación abierta
  Cuando registro un monto mayor al umbral configurado
  Entonces el sistema marca la operación como "Inusual"
  Y notifica al Oficial de Cumplimiento
```

Reglas:

- Un escenario por comportamiento verificable
- Lenguaje de negocio, sin detalles de UI o implementación
- Mínimo el flujo feliz; casos de error pueden refinarse post-aprobación (ver [pre-análisis](./05.14.pre_analysis_standard.md))
- Sin criterios verificables la historia no cumple la [Definition of Ready](./05.3.DoR.md)

---

## Cómo dividir una historia grande

Dividir por **valor entregable**, no por capa técnica (no "historia de backend" + "historia de frontend").

| Estrategia | Ejemplo |
|---|---|
| Por flujo | Alta, consulta, edición, baja |
| Por regla de negocio | Cálculo normal → cálculo con excepciones |
| Por rol | Vista del analista → vista del supervisor |
| Por datos | Un tipo de documento → todos los tipos |
| Flujo feliz primero | Caso base → validaciones y errores |

## Ejemplo completo

**Historia**

> **Como** Oficial de Cumplimiento, **quiero** ver en una sola pantalla las operaciones inusuales pendientes de dictamen, **para** priorizar su revisión antes del plazo regulatorio.

**Criterios de aceptación**

```gherkin
Escenario: Listado de pendientes ordenado por vencimiento
  Dado que existen operaciones inusuales sin dictamen
  Cuando abro la bandeja de pendientes
  Entonces veo las operaciones ordenadas por fecha límite ascendente

Escenario: Sin pendientes
  Dado que no hay operaciones inusuales sin dictamen
  Cuando abro la bandeja de pendientes
  Entonces veo un mensaje indicando que no hay pendientes
```

**Wireframe:** enlace al boceto (obligatorio si hay interacción de usuario).

## Antipatrones

- **Historia técnica disfrazada**: "Como desarrollador quiero migrar la tabla X". Va como Task, no como historia
- **Historia épica**: no cabe en un sprint ni se puede estimar. Dividir o registrar como Epic
- **Solución impuesta**: el "cómo" en la acción cierra opciones al desarrollador
- **Sin beneficio**: no hay forma de priorizar ni de discutir alcance
- **Criterios ambiguos**: "debe ser rápido", "debe verse bien". Hacerlos medibles
