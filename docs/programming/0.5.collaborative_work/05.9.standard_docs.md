# Guía de Estándares de Documentación

## Introducción

Este documento establece los lineamientos y estándares que los equipos deben seguir para mantener una documentación estructurada, consistente y actualizada. La documentación es parte integral del ciclo de desarrollo y no un entregable opcional; su ausencia bloquea la integración de código al repositorio.

**La documentación es el punto de partida de todo trabajo:** primero la spec validada ([05.15](./05.15.spec_first_workflow.md)), luego el código.

La documentación en SCISA se divide en tres tipos, con propósitos y audiencias distintos. **Todos se publican en el portal wiki.js** ([07.9](../0.7.repositories/07.9.docs_portal.md)). Docusaurus está deprecado.

| Tipo | Audiencia | Fuente de verdad | Publicación |
|---|---|---|---|
| Documentación técnica (Features BDD) | Equipo de desarrollo | Repositorio (`/docs/features/`) | Portal (sincronizado) |
| Architecture Decision Records (ADR) | Equipo de ingeniería | Repositorio (`/docs/adr/`) | Portal (sincronizado) |
| Manuales de usuario | Cliente final | Portal wiki.js | Portal (nivel Cliente) |

## Parte I — Documentación Técnica (Features BDD)

### 1.1 Propósito

Describir el comportamiento esperado de cada feature desde una perspectiva funcional y técnica, usando BDD. Esta documentación vive junto al código y evoluciona con él.

### 1.2 Ubicación en el repositorio

```
/docs
└── features/
    ├── <feature>/
    │   ├── <feature>.feature     ← fuente de verdad (Gherkin en español)
    │   └── <feature>.md          ← contexto + escenarios exportados del .feature
    └── ...
```

Cada feature tiene su propia carpeta en `kebab-case`, consistente con el nombre usado en el backlog y los tickets.

### 1.3 Contenido de cada feature

#### `<feature>.feature` — Escenarios BDD (fuente de verdad)

Escenarios en **Gherkin en español** (`# language: es`, `Dado / Cuando / Entonces`), cubriendo flujos felices y casos borde. Es la spec validada. Ver reglas y ejemplo en [05.15](./05.15.spec_first_workflow.md#idioma-y-formato-gherkin-en-español).

#### `<feature>.md` — Documentación legible

Contiene:

- **Descripción general:** qué problema resuelve y cuál es su alcance.
- **Actores involucrados.**
- **Precondiciones.**
- **Dependencias.**
- **Notas técnicas relevantes.**
- **Escenarios:** bloque **exportado desde el `.feature`** entre marcadores `<!-- feature:start -->` / `<!-- feature:end -->`. No se edita a mano.

Plantilla completa en [13.4](../0.13.templates/013.4.feature_template.md).

### 1.4 Regla de protección de rama — Documentación obligatoria en PRs

El repositorio debe bloquear el merge de un PR que agregue o modifique código de un feature sin su documentación. Se implementa con un pipeline que corre sobre cada PR hacia las ramas protegidas:

1. Si el PR no toca nada en `docs/features/`, **falla**.
2. Si cambia un `.feature` y el bloque exportado del `.md` no coincide, **falla**.

La Branch Policy debe tener activas: mínimo un revisor, *Build validation* con la opción de bloquear si falla, y (recomendado) work items vinculados.

Ejemplo (Azure DevOps):

```yaml
trigger: none

pr:
  branches:
    include:
      - master
      - development

pool:
  vmImage: ubuntu-latest

steps:
  - checkout: self
    fetchDepth: 0

  - script: |
      CHANGED=$(git diff --name-only origin/$(System.PullRequest.TargetBranch)...HEAD)
      HAS_DOCS=$(echo "$CHANGED" | grep -c "^docs/features/" || true)

      if [ "$HAS_DOCS" -eq 0 ]; then
        echo "##[error] Este PR no incluye cambios en docs/features/."
        echo "##[error] Agrega o actualiza el .feature y el .md en docs/features/<feature>/."
        exit 1
      fi
      echo "Documentación presente."
    displayName: "Validar presencia de documentación en docs/features"
```

> **Nota:** configuración de ejemplo. La validación de consistencia `.feature` ↔ `.md` está pendiente de la herramienta de exportación.

### 1.5 Responsabilidades

| Rol | Responsabilidad |
|---|---|
| Analista + par | Escribir la spec antes del desarrollo |
| Validador (par distinto) | Validar la spec y registrar la aprobación en ClickUp |
| Desarrollador | Copiar la spec al repo, mantenerla consistente con el código y exportar el `.md` |
| Revisor del PR | Verificar que escenarios e implementación coinciden |
| Tech Lead | Mantener el estándar de calidad de la documentación técnica |

## Parte II — Manuales de Usuario

### 2.1 Propósito

Guiar al cliente final en el uso de los productos de SCISA. Claros, visuales y estructurados por producto y módulo, sin requerir conocimiento técnico previo. El estándar de redacción está en [05.10](./05.10.user_manual_standard.md).

### 2.2 Tecnología y ubicación

Los manuales se alojan en el **portal wiki.js** ([07.9](../0.7.repositories/07.9.docs_portal.md)), en el espacio *Manuales* con acceso de nivel **Cliente** (lectura). Para el track on-premise, los manuales también aparecen en el wiki del cliente ([07.7](../0.7.repositories/07.7.client_wiki_standard.md)).

La jerarquía de contenido sigue tres niveles:

1. **Producto** (`pld`, `siglo`, etc).
2. **Módulo** (`configuracion`, `reportes`, `usuarios`).
3. **Manual:** documento con la guía de uso de una funcionalidad.

### 2.3 Ciclo de actualización

1. Al cerrar un entregable, el equipo identifica qué funcionalidades visibles para el usuario cambiaron.
2. Se actualiza el manual correspondiente en el portal.
3. Una persona distinta al autor revisa que el manual coincida con el sistema.
4. El manual se mantiene alineado con la versión **en producción del cliente**.

### 2.4 Responsabilidades

| Rol | Responsabilidad |
|---|---|
| Desarrollador / Analista | Redactar los cambios en el manual al cerrar un entregable |
| Responsable de producto | Revisar que el manual refleje la funcionalidad entregada |
| DevOps / Infraestructura | Operar el portal |

## Parte III — Architecture Decision Records (ADR)

### 3.1 ¿Qué es un ADR?

Documento corto que registra una decisión arquitectónica significativa: qué se decidió, por qué, qué alternativas se consideraron y qué consecuencias tiene. No documenta cómo funciona el sistema, sino el *razonamiento* detrás de las decisiones de diseño.

Cada ADR es inmutable una vez aceptado: no se edita, se *supercede*. Si la decisión cambia, se crea un nuevo ADR que referencia y reemplaza al anterior.

### 3.2 Ubicación

```
/docs
└── adr/
    ├── 0001-<titulo-de-la-decision>.md
    ├── 0002-<titulo-de-la-decision>.md
    └── ...
```

Número secuencial de cuatro dígitos permanente e irrepetible, seguido de un título en `kebab-case`.

Plantillas de referencia:

- [Michael Nygard](https://github.com/joelparkerhenderson/architecture-decision-record/tree/main/locales/en/templates/decision-record-template-by-michael-nygard)
- [EdgeX Foundry](https://github.com/joelparkerhenderson/architecture-decision-record/tree/main/locales/en/templates/decision-record-template-by-edgex)

## Resumen comparativo

| Criterio | Documentación técnica | Manuales de usuario | ADR |
|---|---|---|---|
| Audiencia | Equipo de desarrollo | Cliente final | Equipo de ingeniería |
| Fuente de verdad | Repo del proyecto | Portal wiki.js | Repo del proyecto |
| Ubicación | `/docs/features/<feature>/` | Espacio *Manuales* | `/docs/adr/` |
| Formato | `.feature` (Gherkin es) + `.md` exportado | Markdown | Markdown |
| Actualización | Por PR / feature | Por entregable | Por decisión arquitectónica |
| Publicación | Portal (sincronizado desde `master`) | Portal | Portal (sincronizado) |
| Validación | Spec validada por un par + check en PR | Revisión por una persona distinta | Revisión por Tech Lead |
