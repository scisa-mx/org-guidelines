# Documentación generada desde Reqnroll

En proyectos .NET Core usamos **Reqnroll** para automatizar los escenarios BDD. Esta guía define cómo aprovechar los `.feature` que ya viven en `tests/**` para generar, sin trabajo manual, la documentación que presentamos: el [Documento de Validación de Entrega](../0.5.collaborative_work/05.17.delivery_validation_doc.md) y la documentación legible de cada feature ([2.7](./2.7.bdd_documentation.md)).

> **Principio:** el `.feature` se escribe una sola vez. Con él se prueba, se documenta y se entrega.

---

## Dónde viven los `.feature`

En el proyecto de pruebas Reqnroll, bajo `tests/`. **No se duplican** en `docs/`: la documentación se genera a partir de ellos. Aunque hoy no estén implementados los features ni su documentación, los proyectos nuevos y los features que se toquen **arrancan ya con este estándar**.

```
tests/
└── Scisa.<Namespace>.Tests.Specs/
    ├── Features/
    │   └── <feature>.feature        ← un archivo por feature, kebab-case
    ├── StepDefinitions/             ← pasos de Reqnroll (C#)
    └── Scisa.<Namespace>.Tests.Specs.csproj
```

Los features existentes sin spec siguen la regla de avance de [05.15](../0.5.collaborative_work/05.15.spec_first_workflow.md): al tocarlos, primero se escribe la spec de caracterización.

Convenciones mínimas:

| Elemento | Regla |
|---|---|
| Idioma | `# language: es` (`Característica`, `Escenario`, `Dado/Cuando/Entonces`) |
| Un archivo por feature | Nombre en `kebab-case`, igual al del backlog |
| Descripción | Bloque *Como / Quiero / Para* bajo el título |
| Valores | Concretos (emails, IDs, estados), nunca abstractos |
| Escenarios | Título que describa el resultado, no los pasos |

---

## Tags

Un *tag* es una etiqueta arriba de un escenario o feature (`@pendiente`). Reqnroll los entiende y permite filtrar pruebas con ellos. El vocabulario es el de [05.15](../0.5.collaborative_work/05.15.spec_first_workflow.md); aquí se explica para qué sirve cada uno al generar documentación:

| Tag | Para qué sirve | Efecto en el documento de entrega |
|---|---|---|
| `@<ticket>` (ej. `@INN-1542`) | Trazabilidad: qué ticket creó o cambió el escenario | Se muestra el ticket junto al escenario |
| `@pendiente` | Comportamiento planeado, aún no implementado. Se omite de la ejecución (`dotnet test --filter "Category!=pendiente"`) | Va a "Fuera de alcance", no a "Escenarios a validar" |
| `@manual` | Escenario que no se automatiza (depende de un tercero, de UI difícil de probar, etc.) | Se marca `Manual` en vez de resultado automatizado, para que QA sepa que debe probarlo a mano |
| `@critico` | Flujo que no debe romperse | Se destaca; es de demo obligatoria en el Gateway |

Sin `@pendiente` y `@manual` el documento no distingue entre "no se hizo" y "no se prueba solo", y QA no sabría qué validar a mano. Los demás son útiles pero no bloquean la generación.

## ¿Hace falta versionar los features?

No hace falta un versionado aparte. Ya tenemos el de la solución:

- Cada release lleva un **tag de git** con su versión semver ([07.3](../0.7.repositories/07.3.semantic_versioning.md)).
- Qué cambió en la entrega se obtiene comparando `tests/**/*.feature` entre el tag anterior y el actual (`git diff <tag-anterior>..<tag-actual> -- tests/`).

Vale la pena: esa comparación alimenta la columna **Nuevo / Modificado / Sin cambios** del documento de entrega, que es justo lo que QA o el cliente necesita para saber qué validar.

| Situación | Estado |
|---|---|
| Escenario no existía en la versión anterior | Nuevo |
| Escenario existía y cambió su texto | Modificado |
| Escenario idéntico | Sin cambios |
| Escenario eliminado | Se lista como "Eliminado" en el resumen de cambios |

Requisito: el release anterior debe tener su tag. Sin tag no hay base de comparación (el primer release se marca todo como Nuevo).

## Qué se genera

| Salida | Origen | Destino |
|---|---|---|
| Documento de Validación de Entrega | `.feature` + resultados de ejecución + `CHANGELOG.md` + diff entre tags | Wiki del cliente / producto (no se guarda en el repo) |
| Documentación legible por feature | `.feature` | Portal ([07.9](../0.7.repositories/07.9.docs_portal.md)); si se versiona en el repo, solo como salida generada |

### Resultado de ejecución

El pipeline del release ejecuta las pruebas con un reporte consumible (por ejemplo `dotnet test --logger "trx;LogFileName=specs.trx"`). El generador cruza el resultado de cada escenario con su fila en el documento.

## Herramienta de generación: por evaluar

La herramienta no está definida. Se evalúa en un spike: [propuesta de evaluación](../../process-proposals/doc_generator_evaluation.md). Es la base del Ticket 2.2 de la [épica de consolidación](../../process-proposals/docs_consolidation_epic.md).

Requisitos mínimos que debe cumplir:

- Lee `.feature` en español, incluidos `Regla:`, `Antecedentes:` y `Esquema del escenario` con sus ejemplos.
- Salida en **Markdown** compatible con wiki.js.
- Cruza resultados de ejecución con escenarios.
- Calcula Nuevo / Modificado / Sin cambios entre dos tags.
- Corre igual en local y en pipeline.

Mientras no exista, el documento de entrega se arma a mano con la plantilla [013.5](../0.13.templates/013.5.delivery_validation_template.md).

## Checklist para el desarrollador

- [ ] Los `.feature` de `tests/**` reflejan el comportamiento entregado en el PR.
- [ ] Todo escenario no pendiente y no manual tiene step definitions y pasa en el pipeline.
- [ ] `CHANGELOG.md` describe el cambio en lenguaje de negocio y con su ticket.
- [ ] El release anterior tiene su tag de git.
